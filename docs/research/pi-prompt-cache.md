# Pi prompt-cache reuse across independent sessions

Research snapshot: 2026-11-07 UTC. This is evidence for planning, not an approved implementation design. No model requests were made; provider claims are documentation, not experimentally verified guarantees. Source links to Pi are fixed at commit [`f9a26365568127461c47a07a37dcb42c140a3ac5`](https://github.com/earendil-works/pi/tree/f9a26365568127461c47a07a37dcb42c140a3ac5); provider pages are live and can change.

## Version and scope

The authoritative Pi project is [earendil-works/pi](https://github.com/earendil-works/pi), the redirect target of badlogic/pi-mono. On the research date, its [latest non-prerelease GitHub release](https://github.com/earendil-works/pi/releases/tag/v1.5.0) was **v1.5.0**, published 2026-11-02, and [npm's latest package](https://registry.npmjs.org/@earendil-works%2Fpi-coding-agent/latest) was also 1.5.0. The [tag ref](https://api.github.com/repos/earendil-works/pi/git/ref/tags/v1.5.0) points to the commit above. Contrary to the task's premise that latest differs from installed 1.5.0, `pi --version` reported 1.5.0; this checks version only, not the installed build's source integrity. The earlier [`@mariozechner/pi-coding-agent` npm package](https://registry.npmjs.org/@mariozechner%2Fpi-coding-agent/latest) has a different latest tag and repository metadata; don't confuse its version with the current package.

We cover the named providers' direct routes and distinguish Pi's subscription paths. OpenAI-compatible third parties, Azure, Bedrock and Claude-on-Google have their own policies and are not assumed equivalent. A common prefix is necessary, but matching it alone does not guarantee a hit: provider scope, routing, minimum length, available writes and retention also matter.

## Short answer: session IDs are route-dependent

**The earlier unqualified suggestion that a new session ID prevents reuse is wrong as a universal statement.** A Pi session ID is not inherently a provider cache key. Pi's SDK gives its agent the session manager's ID, and the agent forwards it as a stream option ([SDK](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/coding-agent/src/core/sdk.ts#L405-L427), [agent](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/agent/src/agent.ts#L476-L482)). Session IDs default to UUIDs, with explicit SDK/CLI overrides ([session format](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/coding-agent/docs/session-format.md#L9-L14)).

* **OpenAI API Responses:** Pi normally sends that ID as `prompt_cache_key`; OpenAI documents that supplied keys separate cache reuse between groups. Thus independent IDs can prevent sharing even with identical prefixes. A shared key affects routing/accounting, not a hit guarantee. Models before GPT-5.6 particularly use a stable key for affinity; GPT-5.6+ route automatically but separate keys still provide separate cache accounting ([Pi Responses](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/api/openai-responses.ts#L360-L370), [OpenAI cache location and keys](https://developers.openai.com/api/docs/guides/prompt-caching#prompt-cache-keys)).
* **Anthropic direct Messages:** Pi uses block cache markers rather than a session-ID cache key; the direct API's documented boundary is workspace and exact prefix, not Pi session. New IDs alone are not documented to block reuse. This is not proof of every OAuth backend's behavior ([Pi request construction](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/api/anthropic-messages.ts#L1153-L1243), [Claude cache sharing](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#cache-storage-and-sharing)).
* **Gemini/Vertex GenerateContent:** Pi's normal request builds content, system instruction, tools and thinking config, with no session ID or explicit cached-content name in that builder. Google documents implicit, prefix-based caching, not a Pi-session-ID key. Separate IDs therefore do not themselves establish a miss; Google does not guarantee a hit ([Gemini adapter](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/api/google-generative-ai.ts#L370-L423), [Vertex adapter](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/api/google-vertex.ts#L480-L530), [Google caching](https://aistudio.google.com/docs/caching?generate-content=true#implicit-caching)).

A shared identifier must not be treated as sufficient, a privacy boundary substitute, or an approved change. Whether a particular child has the same *serialized* prefix as its parent remains an empirical question.

## OpenAI: APIs and subscriptions

**Provider contract.** OpenAI caches the full rendered prefix, including provider instructions, developer text, tools and conversation. Changes to tool names/descriptions/schemas/order, model, `parallel_tool_calls`, reasoning effort, output settings or compaction can change the prefix. GPT-5.6+ can use configuration updates for supported mid-conversation effort changes. For GPT-5.6+ the minimum is 1,024 visible input tokens; earlier-model thresholds vary with model/settings. OpenAI selects eligible longest matching breakpoints; models differ in explicit/implicit breakpoints and reporting. Caches are isolated across organizations and regional processing boundaries, stored per machine and subject to routing/eviction. The OpenAI documentation says request keys separate reuse groups but do not pin a machine ([prefix/settings](https://developers.openai.com/api/docs/guides/prompt-caching#which-settings-affect-the-cached-prefix), [how caching works](https://developers.openai.com/api/docs/guides/prompt-caching#how-caching-works), [location and keys](https://developers.openai.com/api/docs/guides/prompt-caching#cache-location)).

**Retention and measurement.** GPT-5.6+ Responses supports `prompt_cache_options.ttl` with 30-minute default minimum and 12-hour option; it may retain longer. Earlier models' `in_memory` is typically 5–10 minutes of inactivity up to one hour, while `24h` can retain up to 24 hours and its default depends on organization retention settings. These are model-specific, not a universal Pi TTL. Usage reports cached input tokens; Pi maps Responses `input_tokens_details.cached_tokens` and `cache_write_tokens` into `cacheRead` and `cacheWrite`, subtracting them from ordinary input. It maps Chat Completions usage separately ([OpenAI lifetime](https://developers.openai.com/api/docs/guides/prompt-caching#cache-lifetime), [Pi Responses mapping](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/api/openai-responses-shared.ts#L632-L646), [Pi completions mapping](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/api/openai-completions.ts#L1514-L1546)).

**Current Pi implementation, not a provider guarantee.** The normal `openai` provider uses Responses with either API key or Sign in with ChatGPT; the latter is a subscription credential on the same provider, not the legacy Codex provider ([provider](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/providers/openai.ts#L9-L30)). For enabled caching, Pi sends the clamped session ID as `prompt_cache_key` and also sends session-affinity/request-ID headers; `none` omits the key. The ChatGPT sign-in branch omits retention/options fields that it says that route rejects, but still builds the key; do **not** assume API-key retention or cache isolation policies apply to subscription traffic without a separate provider statement ([Responses auth and headers](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/api/openai-responses.ts#L45-L55), [headers](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/api/openai-responses.ts#L300-L335), [body](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/api/openai-responses.ts#L360-L370)).

`openai-codex` is a **legacy separate** ChatGPT Plus/Pro subscription backend at `chatgpt.com/backend-api`; Pi puts the enabled session ID in `prompt_cache_key` and session headers, and can pool WebSockets by session. A WebSocket's five-minute idle expiry is a connection lifetime, not documented provider cache TTL. Its exact provider-side reuse/isolation and subscription billing are unverified; do not transfer direct API guarantees ([provider](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/providers/openai-codex.ts#L6-L20), [body](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/api/openai-codex-responses.ts#L568-L580), [headers](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/api/openai-codex-responses.ts#L1687-L1696), [Pi library documentation](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/README.md#L1872)). Chat Completions is a further distinct adapter: for direct OpenAI it likewise maps the session ID to the key, and sends `24h` only for supported long retention ([source](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/api/openai-completions.ts#L805-L817)).

Pi defaults its Responses retention preference to `short`; `PI_CACHE_RETENTION=long` or an explicit option changes it. Depending on model compatibility, long maps to `24h` or `prompt_cache_options.ttl: 30m`; `none` can request explicit mode where supported. The preference names are **not** promises of actual lifetime and do not universally disable provider-side implicit caching ([source](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/api/openai-responses.ts#L80-L88), [mapping](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/api/openai-responses.ts#L124-L140)).

## Anthropic: Messages API versus Claude subscription

**Provider contract.** Anthropic's cumulative cache prefix is `tools → system → messages`; a breakpoint writes the exact prefix and lookup searches backward at most 20 block positions per breakpoint, with up to four breakpoints. Identical text/images and workspace/organization isolation matter. Tool-definition changes invalidate all following levels; thinking configuration and effort invalidate message blocks and may invalidate earlier levels depending on model. Some newer models support appended system/tool/effort changes that preserve prior prefixes. Preserved versus stripped thinking blocks also changes reuse depending on model and message type ([structure/lookback](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#structuring-your-prompt), [invalidation](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#what-invalidates-the-cache), [thinking](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#caching-with-thinking-blocks), [sharing](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#cache-storage-and-sharing)).

The default ephemeral lifetime is five minutes refreshed by use; one-hour markers are available at additional cost. Lifetime starts at request start, not response completion. Cacheable length is model dependent: for example Opus 5.5 is 512 tokens, Sonnet 5 is 1,024 and Opus 4.6 is 4,096; below the threshold the API may silently not cache. For concurrent calls, the entry becomes available only after the first response starts. `cache_read_input_tokens`, `cache_creation_input_tokens`, and `input_tokens` are distinct buckets ([lifetime](https://platform.claude.com/docs/en/build-with-claude/prompt-caching), [minimum and concurrency](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#explicit-cache-breakpoints), [usage](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#tracking-cache-performance)).

**Current Pi implementation.** Pi's direct provider supports API key and Claude Pro/Max OAuth ([provider](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/providers/anthropic.ts#L74-L90)). Its default is short ephemeral markers; long requests `ttl: 1h` where compatible, and `none` suppresses markers ([retention](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/api/anthropic-messages.ts#L71-L98)). It marks the initial system text, last tool when supported, and the last eligible user/system block; newer compatible models can use native tool-change blocks ([system and tools](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/api/anthropic-messages.ts#L1219-L1265), [last message](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/api/anthropic-messages.ts#L1524-L1552), [last tool](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/api/anthropic-messages.ts#L1629-L1656)). OAuth adds an identity system block and renames tools, so API-key and OAuth serialized prefixes are not automatically identical. OAuth does not follow the optional compatibility session-affinity-header branch used by some non-direct providers ([OAuth](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/api/anthropic-messages.ts#L1041-L1069), [OAuth system](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/api/anthropic-messages.ts#L1219-L1243), [tool names](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/api/anthropic-messages.ts#L1649-L1655)). Direct API documentation is not an independently verified subscription-cache SLA. Pi maps Anthropic read/write and 1h write tokens into usage ([source](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/api/anthropic-messages.ts#L715-L726)).

## Google: Gemini API and Vertex AI

**Provider contract.** Gemini GenerateContent implicit caching is on by default for Gemini 2.5 and newer; similar prefixes soon after one another improve chances but savings are not guaranteed. The current table lists 2,048 minimum tokens for Gemini 2.5 Flash/Pro and 4,096 for listed Gemini 3/4 models. Gemini 4 Argon and newer additionally require at least 2,050 newly added tokens to cache the entire previous request; output, thoughts and function results count. Cached input is reported in `usage_metadata`. Explicit cache objects are a distinct feature, with default one-hour TTL, supported on eligible Gemini 2.5/3 models but not Gemini 4 Argon onward; the Interactions API has different support and is not Pi's GenerateContent path ([Google GenerateContent caching](https://aistudio.google.com/docs/caching?generate-content=true)). Google does not state a firm implicit TTL in that Gemini API page; do not import explicit TTL as implicit TTL.

Vertex's separate Google Cloud documentation says implicit caching defaults on, with in-memory and durable tiers; entries expire no later than 24 hours after creation, most earlier, and supported models vary. Explicit caches have separate storage costs; implicit cache hits are reported via `cachedContentTokenCount`. Cloud project configuration and regional boundaries must not be conflated with Gemini API credentials; the cited page does not establish that arbitrary projects or accounts share a cache ([Vertex context caching](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/context-cache/context-cache-overview#implicit-caching)).

**Current Pi implementation.** `google` uses the Gemini API with an API key, while `google-vertex` supports Google Cloud API key or ADC/service-account credentials ([Gemini provider](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/providers/google.ts#L6-L14), [Vertex auth](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/providers/google-vertex.ts#L8-L24)). Both call GenerateContent streaming; their normal builders serialize system instructions, tools, and thinking options but do not create or reference an explicit cache object. No documented Pi session-ID cache control or guarantee of Google implicit-cache behavior for thinking changes was found. Both adapters map `cachedContentTokenCount` to `cacheRead`, and report `cacheWrite: 0`; zero write is an adapter representation, not proof no cache was created ([Gemini call](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/api/google-generative-ai.ts#L85-L100), [Gemini builder](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/api/google-generative-ai.ts#L370-L423), [Gemini usage](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/api/google-generative-ai.ts#L230-L246), [Vertex builder](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/api/google-vertex.ts#L480-L530), [Vertex usage](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/ai/src/api/google-vertex.ts#L245-L261)).

## Pi context, compaction and extension surface

The system prompt and tool loadout are part of the transcript; Pi can append prompt/tool changes for compatible models, or replay a full checkpoint for others. This means equal human-visible instructions do not establish equal serialized prefix, particularly across working directories, loaded context files, active tool definitions/order, auth modes and model capabilities ([Pi extensions](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/coding-agent/docs/extensions.md#L615-L659), [tool transitions](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/coding-agent/docs/extensions.md#L2633-L2639)).

Compaction replaces older context with a summary and a replayed system/tool checkpoint; the part after the first changed prefix position cannot be assumed reusable, though an unchanged earlier prefix may remain reusable. Pi's summarization call sets `cacheRetention: none` and uses the supplied routing ID or a fresh one; that is an implementation preference, **not** proof that every provider disables implicit reads/writes ([session format](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/coding-agent/docs/session-format.md#L124-L135), [summarization](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/coding-agent/src/core/compaction/compaction.ts#L618-L637)). Pi also has conditional cache warming and usage totals; warming is not free and may itself create usage ([settings](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/coding-agent/docs/settings.md#L20-L23), [usage entries](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/coding-agent/docs/session-format.md#L114-L121)).

**Documented extension capabilities:** `before_agent_start` can adjust structured system-prompt inputs and active tools; `context` and `context_with_system` transform request context; `session_before_compact` can cancel/customize compaction; `before_provider_request` inspects or replaces the serialized payload. `ctx.sessionManager.getSessionId()` is documented read-only access. Payload interception is provider-specific and can change what is sent without changing `ctx.getSystemPrompt()`; reading an ID is not a documented extension setter for the agent's provider cache ID. Internal adapter functions and session fields above are evidence of present behavior, not stable extension APIs ([prompt](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/coding-agent/docs/extensions.md#L615-L659), [context](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/coding-agent/docs/extensions.md#L815-L844), [compaction](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/coding-agent/docs/extensions.md#L532-L566), [payload](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/coding-agent/docs/extensions.md#L864-L879), [session manager](https://github.com/earendil-works/pi/blob/f9a26365568127461c47a07a37dcb42c140a3ac5/packages/coding-agent/docs/extensions.md#L1201-L1203)).

## Remaining uncertainty

* Subscription backend cache isolation, billing and guarantees are not established by direct API cache docs; Pi's serialized request is observable in source but is not a service contract.
* Exact Google implicit cache scope, TTL on Gemini API, and the effect of particular thinking/tool changes are not fully specified in the sources reviewed; absence of an ID in the Pi request does not prove cross-session hits.
* The parent/child workload's actual payload equivalence and cache metrics have not been measured. Any later authorized observation should avoid recording private prompts, credentials or other sensitive payloads, and must account for model-call cost. This research did not make paid calls.
