# Dispatch and the installed cached-compaction extension

Research for [issue #11](https://github.com/wh3at/pi-orca-dispatch/issues/11) (no comments). This is an implementation comparison, not a change proposal or evidence of a cache hit. Repository baseline: `7839a3c` (dispatch 0.2.2). No private session contents, extension logs, credentials, or paid requests were inspected.

## Executive answer

`pi-cached-compaction` reuses the prefix of **a request already made in the same running session** to generate a compaction summary. It captures a model-visible transcript and provider payload, appends a summary instruction, rebuilds and compares the provider request, and falls back if its checks fail. It does not clone its in-memory capture or generally transfer the parent's full conversation cache to an independent child. An eligible provider-specific shared **system-prefix** cache is separate from that same-session compaction mechanism.

Dispatch copies the active persisted branch into a new session ID and starts another Pi process. That preserves useful history, not the parent's last serialized request, transport affinity, process-local extension state or guaranteed current tool definitions/order. Even identical IDs for copied *entries* are not identical session/cache IDs. Some prompt-prefix reuse may happen under provider-specific conditions; neither a cache key nor copied history proves a hit. Do not alter the parent or replace the child conversation with a summary just to obtain reuse.

## What the installed extension actually does

1. **Capture is live and process-local.** At `context_with_system` it saves the transcript, and at `before_provider_request` captures the payload, model and time; Claude bridge instead captures on `message_start`. The stored payload includes changes made by earlier payload handlers, not later ones. Compaction, model selection and tree navigation discard the capture; session startup does not reconstruct it from the saved session. See [index.ts:94–103, 214–231, 238–284](https://github.com/nicobailon/pi-cached-compaction/blob/e1e20de0a7e433070414602f1105cdcac258ef4f/index.ts#L214-L284). Pi documents chained hooks in load/registration order and `context_with_system` ownership of the leading system and tool state ([reference](https://github.com/earendil-works/pi/blob/v1.5.0/packages/coding-agent/docs/extensions.md#context_with_system)). A later transform can invalidate the captured picture.
2. **Availability is inferred, not a reservation.** Same provider/model, a captured request, a usable `messages` or `input` array, append-only branch correspondence and positive cache read/write on a successful prior assistant are required; known expired cache and overflow fall back. Lifetime uses declared model TTL, reported tiers, explicit OpenAI minimum, or Kimi rules. If lifetime is unknown, `expiresAt` is undefined and the code still permits the cached path, which can be cold; countdown and pre-expiry action are unavailable ([index.ts:269–308](https://github.com/nicobailon/pi-cached-compaction/blob/e1e20de0a7e433070414602f1105cdcac258ef4f/index.ts#L269-L308), [cache-state.ts:23–52](https://github.com/nicobailon/pi-cached-compaction/blob/e1e20de0a7e433070414602f1105cdcac258ef4f/cache-state.ts#L23-L52)). Identity matching for ordinary messages is role/timestamp (plus tool-call ID for tool results), with special custom-message handling, not an exhaustive content comparison; the later payload check supplies a further guard ([cached-request.ts:34–63](https://github.com/nicobailon/pi-cached-compaction/blob/e1e20de0a7e433070414602f1105cdcac258ef4f/cached-request.ts#L34-L63)).
3. **Message placement and summary.** It uses Pi's `firstKeptEntryId`, finds a text preview of the first retained model-visible message, handles repeated previews by counting from the end, then sends captured transcript + new messages + a user summary instruction. It asks for a checkpoint *before* the retained messages and folds previous summaries into it; image-only/thinking-only first retained messages fail closed. Returned compaction retains Pi's boundary and token count and merges prior file-list details. The model still sees retained messages, so faithful boundary obedience is a model behavior, not a mathematical guarantee ([cached-request.ts:136–217, 234–250](https://github.com/nicobailon/pi-cached-compaction/blob/e1e20de0a7e433070414602f1105cdcac258ef4f/cached-request.ts#L136-L217); [index.ts:323–405](https://github.com/nicobailon/pi-cached-compaction/blob/e1e20de0a7e433070414602f1105cdcac258ef4f/index.ts#L323-L405)). Pi's own projection after compaction uses a summary and retained entries; its ordinary summary serializes messages and truncates tool results at 2,000 characters ([Pi compaction reference](https://github.com/earendil-works/pi/blob/v1.5.0/packages/coding-agent/docs/compaction.md#message-serialization)). Full cached-path tool outputs are still only what was present in the live model transcript; bridge preview limitations apply.
4. **Comparison is structural with intentional exclusions, not literal wire bytes.** The new call uses the current thinking level, session ID, bounded output, abort signal and `streamSimple` + `onPayload`. Missing top-level fields from the captured payload are copied into the rebuilt payload, then top-level fields and initial message-array elements are JSON-compared, ignoring `cache_control`, output limit keys, and OpenAI Responses `tool_choice` where applicable; trailing effort/configuration items are excluded. A mismatch aborts/falls back. Headers and later extension transforms are not verified. Non-OpenAI providers retain tool declarations and are instructed not to call; a tool call, empty/length/error result falls back. OpenAI Responses sets tool choice none. Bridge uses a fork header and no payload comparison ([cached-request.ts:65–134](https://github.com/nicobailon/pi-cached-compaction/blob/e1e20de0a7e433070414602f1105cdcac258ef4f/cached-request.ts#L65-L134); [index.ts:331–387](https://github.com/nicobailon/pi-cached-compaction/blob/e1e20de0a7e433070414602f1105cdcac258ef4f/index.ts#L331-L387)). This assumes provider schemas, field semantics, JSON order and cache behavior; it is not a general Pi guarantee.
5. **Separate shared key optimization.** Only `openai-responses` models with `compat.supportsExplicitPromptCacheMode === true` and `PI_CACHE_RETENTION=long` get a candidate key: `pi-` + first 40 hex characters of SHA-256 of `ctx.cwd`. Even then rewriting requires an existing string `prompt_cache_key`, object `prompt_cache_options`, `input` array, and a first developer message whose content is a string; it replaces the key and puts a 12-hour explicit breakpoint on that developer text ([index.ts:66–74, 214–225](https://github.com/nicobailon/pi-cached-compaction/blob/e1e20de0a7e433070414602f1105cdcac258ef4f/index.ts#L66-L74); [cached-request.ts:107–119](https://github.com/nicobailon/pi-cached-compaction/blob/e1e20de0a7e433070414602f1105cdcac258ef4f/cached-request.ts#L107-L119)). CWD is not a content hash, account boundary, or proof the developer prompt and tool schemas match. For ordinary Pi 1.5.0 Responses the payload key normally derives from session ID; selected compatible chat completions do likewise ([Responses](https://github.com/earendil-works/pi/blob/v1.5.0/packages/ai/src/api/openai-responses.ts#L360-L369); [completions](https://github.com/earendil-works/pi/blob/v1.5.0/packages/ai/src/api/openai-completions.ts#L790-L816)). The extension's override is deliberately narrower. Kimi long-cache option and bridge fork are different special cases, not portable cache IDs.
6. **Cost and side effects.** By default interactive mode requests long retention and expiry compaction only at >=140k tokens, idle, no queued work, auto-compaction enabled and cached-path checks pass; unknown lifetime means no timer. Environment already explicitly set is respected. Extension compaction uses a model request, changes that session's context and writes traces which can contain excerpts around request mismatches; do not copy logs or payloads into shared telemetry ([config.ts:12–41](https://github.com/nicobailon/pi-cached-compaction/blob/e1e20de0a7e433070414602f1105cdcac258ef4f/config.ts#L12-L41); [index.ts:80–92, 148–181](https://github.com/nicobailon/pi-cached-compaction/blob/e1e20de0a7e433070414602f1105cdcac258ef4f/index.ts#L148-L181); [README:60–66, 103–116](https://github.com/nicobailon/pi-cached-compaction/blob/e1e20de0a7e433070414602f1105cdcac258ef4f/README.md#L60-L66)). Its price comparisons are estimates and provider-dependent, not dispatch measurements.

## Dispatch: preserved state versus reconstructed requests

* The command waits for idle and checks session generation; captures current provider/model identity, thinking level and active tool names ([index.ts:178–203](https://github.com/wh3at/pi-orca-dispatch/blob/7839a3c/index.ts#L178-L203)). Before its first await, dispatch captures the in-memory active branch, not other branches; it JSON-copies and validates a linear parent chain and compaction references. It never opens/switches the parent session. Preflight precedes creation; generation is checked again. Child file gets a fresh UUID/header, optional parent path as metadata, original branch entry IDs/content, and a final `session_info` title; exclusive creation and restrictive permissions protect existing files ([session.ts:57–145, 148–210](https://github.com/wh3at/pi-orca-dispatch/blob/7839a3c/src/session.ts#L57-L145); [dispatch.ts:47–76](https://github.com/wh3at/pi-orca-dispatch/blob/7839a3c/src/dispatch.ts#L47-L76)). Separate session files do not isolate the shared working directory or external effects.
* The raw copy includes system messages/checkpoints, custom entries, context edits, model/thinking history and compactions where present, **not** necessarily a verbatim request. Pi 1.5.0 projection applies the latest compaction and context edits and rebuilds the model-visible conversation; custom metadata is not model-visible, but custom messages are. System messages and compaction checkpoints can persist prompt/tool deltas. Current resource discovery, startup hooks, per-turn `before_agent_start`/`context`/`context_with_system`, provider serialization and payload hooks still affect the outgoing request ([Pi session format](https://github.com/earendil-works/pi/blob/v1.5.0/packages/coding-agent/docs/session-format.md#context-building); [Pi extension lifecycle](https://github.com/earendil-works/pi/blob/v1.5.0/packages/coding-agent/docs/extensions.md#lifecycle-overview)). An extension may reconstruct its own state from branch entries (the official todo example does), but live closures, pending queues, network handles, captured final payload and unpersisted external state are not copied by dispatch.
* Launch keeps an allowlist of resource flags in their original relative order, including explicit system-prompt flags, but not the original session, prompt, credentials or arbitrary CLI options; it passes child session, provider, model, thinking, one observer and `@taskFile` ([launch-plan.ts:8–32, 53–72](https://github.com/wh3at/pi-orca-dispatch/blob/7839a3c/src/launch-plan.ts#L8-L32); [dispatch.ts:59–104](https://github.com/wh3at/pi-orca-dispatch/blob/7839a3c/src/dispatch.ts#L59-L104)). The spawned process inherits the launcher's environment, not a serialized snapshot of the parent's entire runtime ([launch.mjs:87–94](https://github.com/wh3at/pi-orca-dispatch/blob/7839a3c/bin/launch.mjs#L87-L94)). Global/project resources are loaded afresh subject to Pi configuration and trust. A same-named model can have different effective endpoint/compat/provider behavior; the job stores only identity, not the model object. Thinking is passed but observer does not independently verify it.
* Observer waits up to 30 seconds for required tool names, verifies provider/model identity, applies the captured active names again just before accepting first input, and fails closed on missing tools or model mismatch. It verifies tool **set membership**, not schema, execution implementation or order; later user changes and session switches are respected ([observer.ts:101–165, 202–285](https://github.com/wh3at/pi-orca-dispatch/blob/7839a3c/observer.ts#L101-L165)). Importantly Pi 1.5.0's tool loadout preserves the order of already active tools and appends newly active ones, ignoring a mere reordering of the same names ([agent-session.ts:1605–1620](https://github.com/earendil-works/pi/blob/v1.5.0/packages/coding-agent/src/core/agent-session.ts#L1605-L1620)). Capturing an array and passing it to `setActiveTools` does not guarantee parent order; identical names do not guarantee identical serialized definitions or even identical initial head after replay. Later hooks can still modify the request.
* The task is appended at child startup after the copied history, rather than rewritten into the head. In the pinned standalone integration, Pi expands `@taskFile` to a `<file name="...">` wrapper around the prompt, not bare prompt bytes ([standalone.test.ts:63–76](https://github.com/wh3at/pi-orca-dispatch/blob/7839a3c/tests/standalone.test.ts#L63-L76)). Its path and task are child-specific suffix input. This placement is compatible in principle with preserving a matching prefix, but provides no guarantee across a new session/transport/model and existing extension transformations.

## Actual README/code mismatches and qualifications

These are concrete observations, not allegations about uninspected providers or private runs:

1. Installed README's “byte for byte” claim ([README:40, 185–190](https://github.com/nicobailon/pi-cached-compaction/blob/e1e20de0a7e433070414602f1105cdcac258ef4f/README.md#L183-L190)) is stronger than its comparison: normalization/exclusions, copied missing fields, unobserved headers and later handlers mean it does not compare all bytes of the final wire request. README itself acknowledges later handlers and bridge limitations ([README:202–207](https://github.com/nicobailon/pi-cached-compaction/blob/e1e20de0a7e433070414602f1105cdcac258ef4f/README.md#L202-L207)).
2. README's four conditions say cache “hasn't expired”; unknown expiry is allowed by code if prior usage indicates caching. The README separately acknowledges the cold-cache risk ([README:185–192, 202–204](https://github.com/nicobailon/pi-cached-compaction/blob/e1e20de0a7e433070414602f1105cdcac258ef4f/README.md#L183-L204)). “Full tool output” is bounded by what the request contained and bridge may use previews ([README:132](https://github.com/nicobailon/pi-cached-compaction/blob/e1e20de0a7e433070414602f1105cdcac258ef4f/README.md#L132)).
3. Dispatch README's unqualified “active branch” capture ([README:70–74, 115–117](https://github.com/wh3at/pi-orca-dispatch/blob/7839a3c/README.md#L70-L74)) has a concrete valid-format exception: Pi 1.5.0 permits a retain-none compaction whose `firstKeptEntryId` equals the compaction's own ID ([session-format](https://github.com/earendil-works/pi/blob/v1.5.0/packages/coding-agent/docs/session-format.md#compactionentry)); dispatch requires that ID be in `previousIds` before adding the compaction itself ([session.ts:91–114](https://github.com/wh3at/pi-orca-dispatch/blob/7839a3c/src/session.ts#L91-L114)), so it rejects that branch. Existing [tests](https://github.com/wh3at/pi-orca-dispatch/blob/7839a3c/tests/session.test.ts#L159-L171) cover dangling/future references, not the valid self-reference. Do not silently change this in research.
4. Dispatch README says instruction is delivered as its first message; the standalone test establishes file-attachment expansion wraps the instruction, so this is semantically true but not a byte-identical raw user message. “Same ... tools” means selected names, subject to fail-closed startup; it does not establish tool order, schemas, executable behavior or final provider declarations. README's “re-applies its model and tool selection” is imprecise: provider/model are CLI-selected and observer **verifies** identity, whereas it explicitly calls `setActiveTools` ([README:70–74, 115–117](https://github.com/wh3at/pi-orca-dispatch/blob/7839a3c/README.md#L70-L74); observer above). Similarly “same folder” is not an isolated worktree. These qualifications matter for cache claims, not necessarily ordinary user-facing meaning.

## Applicability, ideas, and regression constraints

* **Reusable principles, not an implementation decision:** keep stable shared prefix early and task-specific text late; observe the actual provider-shaped request, compare relevant prefix/settings rather than assuming raw JSONL implies equality, and fall back safely when identity, provider support, schema, tool order, prompt or freshness cannot be established. Keep payloads in memory and report only safe metadata; the extension's mismatch excerpts can disclose conversation content. Actual cost/read metrics are provider responses, not key equality.
* The extension can perform its normal cached compaction **inside a child after that child has made and captured its own eligible request**. Parent's in-memory capture does not transfer. Its cwd-shared explicit 12h developer prefix can independently benefit eligible parent/child sessions when the same extension, model capability, retention, payload shape, cache scope and identical prefix apply. It does not assert the parent's full conversation is shared. New session ID normally changes session-scoped affinity, while provider caches may also be affected by routing, TTL, capacity and provider-specific prefix rules. Bridge temporary fork is of the bridge's live conversation and is not an independent Pi-child cloning API.
* Preserve independent child UUID/file, active branch and compaction semantics, existing task meaning, startup fail-closed checks, no parent session writes/switches, later user model/tool control and launch idempotence. Never pre-compact or inject instructions into the parent as an optimization, share a parent session file, reorder tools silently, suppress working tools, or claim cache success merely because a key matches. Provider-specific key sharing needs privacy/scope review and exact-prefix validation; sharing cwd-derived affinity across unrelated sessions can have operational implications.
* Regression coverage should include compaction checkpoints (including retain-none), context edits/custom messages, system prompt/tool deltas, extension hook order, late tools and same-name changed schemas, reordered active names, model fallback/thinking, new UUID and unchanged parent bytes, first-input wrapper, nested dispatch, unsupported/cold cache and overflow/fallback. Existing tests cover active branch, parent immutability, copying compaction/extension state, startup model and delayed tools, and standalone no-paid-request launch ([session tests](https://github.com/wh3at/pi-orca-dispatch/blob/7839a3c/tests/session.test.ts#L55-L118); [launcher tests](https://github.com/wh3at/pi-orca-dispatch/blob/7839a3c/tests/launcher.test.ts#L169-L265); [standalone](https://github.com/wh3at/pi-orca-dispatch/blob/7839a3c/tests/standalone.test.ts#L17-L85)). They do not establish live provider cache hits or final-payload equality.

## Validation and open limits

Inspected source and docs only; no private session/log/auth reads, no user config or dependency edits, and no paid API calls. `npm test`: 93 passed, 0 failed, 1 standalone test skipped because its opt-in binary variable was not set. `npm run check`: passed. Opt-in `PI_TEST_STANDALONE=<pinned 1.5.0 binary> npm run test:standalone`: 1 passed using the checksum-pinned local binary and synthetic fixtures, without a paid request. Source conclusions do not replace an isolated synthetic offline payload-serialization test or the separate latest-Pi compatibility research; no implementation or provider behavior was experimentally changed or asserted universally.
